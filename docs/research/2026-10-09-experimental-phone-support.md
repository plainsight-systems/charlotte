# Capture the crash, then shrink Charlotte for phones

**Date:** 2026-10-09
**Method:** desk research, sources cited inline, and an audit of this repository at commit `3d1a366`. Figures marked planner arithmetic come from running the real planner natively over the three pinned model files. The only phone evidence is one iPhone run (Chrome, iOS 26) that passed the GPU check, downloaded Qwen3 0.6B, and then failed to load or run with an error nobody captured.

Charlotte can be tried on phones without touching its kernels' arithmetic or its buffer layout, but not with its desktop load policy. The iPhone run most likely died on memory. Under the default 2 GiB budget the planner creates about 2 GiB of GPU buffers for Qwen3 0.6B the moment a load begins, three quarters of it KV cache that exists only because the budget allows it. That's above the roughly 1.5 GB page limit that a WebKit engineer describes and a third party measured on an iPhone, and when iOS kills a page for memory it leaves no message, which fits a failure nobody could capture. Both phone browsers grant every WebGPU limit Charlotte asks for, because it asks only for the spec defaults. So limits aren't the problem. Memory, command-buffer behaviour and compiler differences are. Two code-level risks rank just behind memory. WebKit has a 2026 report of exactly the override-expression workgroup arrays Charlotte's matmul and attention kernels declare failing to build. And a WebKit bug shows two command buffers in flight hanging silently on iOS, which is Charlotte's normal decode pattern. The plan is to make failures visible and persistent first, rerun the iPhone once unchanged to learn what actually killed it, and then apply a phone memory budget (768 MiB on iOS, 1 GiB on Android). After that come the kernel declaration rewrite and a cap of 128 prompt tokens per step with one step in flight. Qwen3 on the iPhone is the first target, because it's the only listed model that every source puts within reach.

A note on evidence. Platform facts below come from the cited sources. Memory and context figures marked **planner arithmetic** come from the codebase audit, which compiled a scratch program against `build/native-release/libcharlotte_core.a` and ran the real `residency::plan_residency` natively over the three pinned model files with WebGPU's default limits. They're the planner's own numbers, not phone measurements. FLOP counts are the audit's arithmetic from the model shapes. Phone timings are inferences.

## Both phone browsers run WebGPU and grant every limit Charlotte requests

WebGPU shipped in Safari 26 on iOS, iPadOS, macOS and visionOS ([WebKit blog](https://webkit.org/blog/16993/news-from-wwdc25-web-technology-coming-this-fall-in-safari-26-beta/)). WKWebView gets it because it's on by default in iOS 26, not through Safari's feature flag ([Apple Developer Forums 770862](https://developer.apple.com/forums/thread/770862)). Every iOS browser, including Chrome on iOS where the test ran, uses WKWebView, so the adapter, the limits, the WGSL compiler and the memory ceilings are all Apple's. **Nothing measured in desktop Chrome transfers to an iPhone**, because Dawn and Tint play no part there. On Android, Chrome is Blink plus Dawn plus Tint emitting SPIR-V for the phone's Vulkan driver ([Vulkanised 2024 slides](https://dev.vulkan.org/user/pages/09.events/vulkanised-2024/vulkanised-2024-brandon-jones-google.pdf)). WebGPU has been on by default since Chrome 121 ([Chrome 121](https://developer.chrome.com/blog/new-in-webgpu-121)). The blocklist on Chromium `main` admits ARM, Qualcomm and Intel GPUs on Android 12 and later, and Imagination GPUs on Android 16 and later. Every other vendor falls into "limited support" ([webgpu_blocklist_impl.cc](https://chromium.googlesource.com/chromium/src.git/+/main/gpu/config/webgpu_blocklist_impl.cc)). Samsung's vendor ID doesn't appear in that file, so Xclipse phones are probably blocked by default. That's medium confidence, because a 2026 paper benchmarked a Galaxy S24 in Chrome ([arXiv 2605.20706](https://arxiv.org/pdf/2605.20706)). One survey finds **73.6% of Android reports get a working adapter** ([web3dsurvey](https://web3dsurvey.com/webgpu)).

Limits aren't where phones fall short. Charlotte requests exactly the spec defaults: 256 MiB buffers, 128 MiB storage bindings, 16 KiB workgroup storage and 256 invocations (`src/core/gpu/device_requirements.h:29-47`). So desktop runs already exercise the limits a phone grants. WebKit refuses to expose an adapter whose limits fall below the defaults. On iOS it sets `maxBufferSize` to max(256 MiB, min(1 GiB, `maxBufferLength`/3)), and on Apple6 (A13) and later it offers 32 KiB workgroup storage and 1,024 invocations ([WebKit HardwareCapabilities.mm](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebGPU/WebGPU/HardwareCapabilities.mm)). An iPhone 14 Pro Max on iOS 26.6.2 reports 1 GB buffers, 32 KB workgroup storage, `shader-f16` and no subgroups ([Nehanth/pooled #207](https://github.com/Nehanth/pooled/issues/207)). On Android, 100% of survey reports grant at least 1 GiB buffers and 128 MiB bindings, and 94% grant 32 KiB workgroup storage ([web3dsurvey maxBufferSize](https://web3dsurvey.com/webgpu/limits/maxBufferSize/platform/Android); [workgroup storage](https://web3dsurvey.com/webgpu/limits/maxComputeWorkgroupStorageSize/platform/Android)). PowerVR and some Adreno 7xx devices report exactly 128 MiB bindings ([web3dsurvey bindings](https://web3dsurvey.com/webgpu/limits/maxStorageBufferBindingSize/platform/Android)), which is a reason to keep requesting the defaults rather than raise them. The audit's heaviest kernel uses 14,720 B of workgroup memory (attention at Llama's head dimension 64). The largest planned buffer is 254 MiB **(planner arithmetic)**. Both sit inside the defaults.

| | Safari and WKWebView on iOS 26 | Chrome on Android |
|---|---|---|
| WebGPU stack | WebKit's own: Metal backend and WebKit's WGSL compiler | Dawn and Tint, SPIR-V to the Vulkan driver |
| Who gets an adapter | Apple4 (A11) family and up in WebKit's code ([source](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebGPU/WebGPU/HardwareCapabilities.mm)) | Android 12+ ARM, Qualcomm, Intel; Imagination on 16+; others blocked ([blocklist](https://chromium.googlesource.com/chromium/src.git/+/main/gpu/config/webgpu_blocklist_impl.cc)) |

## A 2 GiB default plans twice what an iPhone page reliably survives

The default `memory_budget` is 2 GiB (`src/core/policy/policy.h:33-38`), and no listed model carries a measured policy (`web/models.json:3-25`). The planner fills weights first, then working buffers, then a KV cache that "takes whatever the budget has left" (`src/core/residency/plan.cpp:18-30`). Every buffer the plan names is created up front at `bllm_load_begin`, before a single weight byte is written (`src/core/residency/upload.h:30-40`; `src/wasm/bindings.cpp:919-920`). The table shows what that means for each model, and what lower budgets give instead.

| Budget **(planner arithmetic)** | Qwen3 0.6B | Llama 3.2 1B | Gemma 3 1B (reserve 4,096) | Gemma 3 1B (reserve 512) |
|---|---|---|---|---|
| 2,048 MiB (today's default) | 15,172 tokens, 2,048 MiB placed | 40,422 tokens, 2,048 MiB | 32,768 tokens, 949 MiB | not computed |
| 1,024 MiB | 5,810 | 7,654 | 32,768, 949 MiB | 32,768, 872 MiB |
| 768 MiB | 3,469 | does not fit (needs 801 MiB) | 2,258 | 6,231 |
| 512 MiB | 1,128 | does not fit | does not fit | does not fit |

Qwen3's 2 GiB plan is 359 MiB of weights, 30 MiB of working buffers and 1,659 MiB of KV cache at 112 KiB per token **(planner arithmetic)**. Gemma is the cheapest 1B model here because 22 of its 26 layers keep a fixed sliding-window ring.

The sources disagree about the iPhone's ceiling, and the disagreement matters. WebKit engineer Ben Nham puts the iPhone WebContent process limit at **"~1.5 GB for most devices"**, higher on iPads, with typed arrays and wasm memory separately capped near 2 GB. Alexey Proskuryakov adds in the same thread that Apple doesn't document these limits ([WebKit Bug 268816](https://bugs.webkit.org/show_bug.cgi?id=268816)). The pooled project measured an iPhone 14 Pro Max on iOS 26.6 and reached the same number from the other side. It found that **WebGPU buffers count against the page's 1,536 MB soft limit like JS memory**. Fresh runs survived to 2.6-3.2 GB, but back-to-back runs were killed at 1,534 and 1,537 MB, so 1.5 GB is "the only limit that holds every time" ([pooled PR #258](https://github.com/Nehanth/pooled/pull/258)). Against both, the May 2026 LlamaWeb paper states that **"Safari tab memory is limited to <500 MB"** on iOS. Its iPhone 15 and 17 Pro Max fit only models of 0.40 GB or less ([arXiv 2605.20706](https://arxiv.org/html/2605.20706v1)). The paper doesn't say how it measured, and pooled's own aggregated reports include low-RAM devices on iOS 26.2 crashing at 100-200 MB of JS memory ([pooled #207](https://github.com/Nehanth/pooled/issues/207)). My reading is that 1.5 GB is a real soft limit on recent 6 GB iPhones, that it drops with uptime and system pressure, and that the paper reflects a tighter device or a state where the limit had already fallen. **The plan hedges toward the low figure.** It starts the iPhone at 512 MiB, where Qwen3 is the only model that fits, and ships 768 MiB as the iOS default only if it survives back-to-back loads. Pooled's own production caps make the same bet: 0.5 GB by default on iPhone and 1 GB at most ([pooled PR #258](https://github.com/Nehanth/pooled/pull/258)).

The other prior art points the same way. WebLLM's tracker shows a 135M model running on iOS 26 Safari while a 3B q4 model downloads and is then killed with no console output. The maintainer judged it unfixable on their side ([web-llm #753](https://github.com/mlc-ai/web-llm/issues/753)). WebLLM's own estimate for Qwen3 0.6B at a 4,096-token context is 1,403 MB in q4f16 ([web-llm config.ts](https://github.com/mlc-ai/web-llm/blob/main/src/config.ts)). A WebKit bug asking for 1 GB buffers on iOS was closed INVALID, with a comment in the thread that "iOS is too likely to jetsam at 1GB" ([WebKit 275958](https://bugs.webkit.org/show_bug.cgi?id=275958)).

Android has no published per-tab ceiling. In LlamaWeb, low-power Adreno 7xx, Mali and PowerVR phones fit only models of 0.40 GB or less, and some Mali and PowerVR runs crashed once a 2,048-token KV cache was added. A Galaxy S24 ran everything ([arXiv 2605.20706](https://arxiv.org/pdf/2605.20706)). The plan uses 1 GiB on Android, which pooled also uses for phones under 8 GB of RAM ([pooled PR #258](https://github.com/Nehanth/pooled/pull/258)). At that budget the planner still fits all three models **(planner arithmetic)**.

One part of Charlotte is already phone-shaped. The load reads OPFS through a sync access handle in 16 MiB chunks straight into the wasm heap and streams them to the GPU (`web/wasm_runtime.js:66-75`; `web/load.js:54`). That's the bounded, never-whole-file pattern LlamaWeb and pooled had to adopt to stop load-time kills ([arXiv 2605.20706](https://arxiv.org/html/2605.20706v1); [pooled PR #258](https://github.com/Nehanth/pooled/pull/258)). The audit estimates the peak wasm heap during load at tens of MiB, against a 512 MiB cap. That's an estimate: the code itself says no peak has been measured (`CMakeLists.txt:177-187`). Android's history of wasm growth failing around 300-500 MB on low-RAM phones ([transformers.js #1319](https://github.com/huggingface/transformers.js/issues/1319)) matters only if that estimate is wrong, so the plan doesn't change the heap cap.

## WebKit's compiler and phone GPUs put three code paths at risk

**Override-expression workgroup arrays.** The notes conflict here. WebKit Bug 268425, "[WGSL] override expressions as array lengths do not compile", was fixed in February 2024 ([WebKit 268425](https://bugs.webkit.org/show_bug.cgi?id=268425)). But a project report on Safari 26.6.2 (macOS, same WebKit as iOS) shows `var<workgroup>` with `array<vec2<f32>, 2u * n>` failing with `GPUValidationError: failed to evaluate override expression`, then `getBindGroupLayout: ComputePipeline is invalid`. `getCompilationInfo()` reports nothing. A bare override (`array<T, n>`) builds, and Chrome builds every variant ([musetric #991](https://github.com/musetric/musetric/issues/991)). Both can be true: the 2024 fix covered the basic case, and the expression case still fails. Charlotte declares exactly the failing form. Matmul's prefill tile is `array<vec4<f32>, 8u * tile_tokens>` (`src/core/kernels/matmul/matmul.wgsl:55`). Attention's `k_tile` is `array<u32, keys_per_tile * (head_dimension / 2u + 1u)>`, and `p_tile` is `queries_per_tile * keys_per_tile`, where `keys_per_tile` and `queries_per_tile` are themselves overrides initialized from expressions (`src/core/kernels/attention/attention.wgsl:30-31, 60-67`). **The plan hedges toward the bug being live**, because the more recent observation names the exact construct. It rewrites each workgroup array length as a bare override that the host computes and passes as a pipeline constant. Every implementation accepts that form, and it changes no arithmetic, so desktop output must stay bitwise identical. If this were the iPhone failure, the page would have named it: the `wgpuComputePipelineGetBindGroupLayout` calls sit inside the build's out-of-memory, validation and internal error scopes (`src/core/kernels/program.cpp:129, 205-213`), and a failed build reports "the model's kernels did not build" with WebGPU's message (`src/wasm/bindings.cpp:513-516`). That's one reason memory, which leaves no message, ranks first.

**Two command buffers in flight.** Charlotte encodes each step as one compute pass in one command buffer, with each launch's pipeline and bind group set inside the pass, and **lets two steps be outstanding** (`src/core/kernels/program.h:38-52`). One pass with many pipeline switches is exactly what WebKit's engineer recommends, since WebKit doesn't coalesce passes or command buffers. In WebKit Bug 311598, though, **two command buffers in flight were enough** to make queue waits on iOS 26 hang indefinitely with no device loss and no error. Attaching Web Inspector hid the problem ([WebKit 311598](https://bugs.webkit.org/show_bug.cgi?id=311598)). Charlotte has no timeout on load or turns (`src/wasm/bindings.cpp:173-176` arms one only for the self-check), so this failure would look like a spinner forever. The plan limits phones to one step in flight. On Android the evidence doesn't require it, but one policy for phones keeps the mode a single configuration. The cost is losing the overlap of one readback per token, which is 0.5 ms median on desktop (`src/core/residency/upload.h:175-181`) and small next to a phone decode step.

**Long prefill command buffers.** A 512-token prefill step is one submit. At 512 tokens it costs about 451 GFLOP of projections for Qwen3, 715 for Gemma and 996 for Llama, with Llama's fused gate and up projection at 34 GFLOP in a single dispatch **(audit arithmetic)**. Desktop Chrome on an M3 Max prefills about 3,200 tokens per second (`docs/research/2026-10-07-chrome-page-benchmark.md:52-64`). The audit infers 0.5-2 s per 512-token step for Qwen3 on a phone and 1.5-5 s for Llama. Neither Apple nor the Android drivers publish a timeout. Metal defines a command-buffer timeout error with no threshold ([Apple MTLCommandBufferError](https://developer.apple.com/documentation/metal/mtlcommandbuffererror-swift.struct/code.md)), and Chromium's GPU watchdog records strikes against origins whose GPU work runs too long ([public-webapps-github, 2021](https://lists.w3.org/Archives/Public/public-webapps-github/2021Dec/0233.html)). Mali and PowerVR runs crashing at a KV depth of 2,048 but not 0 fit the same pattern ([arXiv 2605.20706](https://arxiv.org/html/2605.20706v1)). The fix doesn't touch buffers or kernels. A step may already carry anywhere from 1 to 512 tokens (`src/core/kernels/interface.h:155`), and `Turn` cuts the prompt in two lines (`src/core/runtime/turn.cpp:21, 27`). A load-policy cap of 128 tokens per step shortens each prefill command buffer about fourfold, at no memory cost. A 128-token step still holds far more than the "several milliseconds of work" WebKit asks each command buffer to carry, so the two constraints don't collide.

On Android the 2026 failures are vendor shader-compiler bugs. On an Adreno 7xx in Chrome 153, 8 of 23 vello pipelines failed with `VK_ERROR_UNKNOWN`, triggered by one struct type used both as a `var<workgroup>` array element and stored whole into storage ([vello #1957](https://github.com/linebender/vello/issues/1957)). Charlotte's workgroup arrays hold only `f32`, `u32` and `vec4` elements, so that trigger isn't present. WebLLM's Adreno phones lose the device at the first submit for unexplained reasons, even with 0.5B models ([web-llm #836](https://github.com/mlc-ai/web-llm/issues/836)), and Pixel 10 PowerVR compute is broken enough that PlayCanvas falls back to WebGL2 ([playcanvas #8874](https://github.com/playcanvas/engine/issues/8874)). Charlotte's kernels use no structs in workgroup memory, no subgroups, no f16 arithmetic and no atomics, which avoids the constructs the 2026 reports blame. Whether a particular driver compiles its 28 Qwen3 pipelines can only be learned on the device. Any such failure arrives as a named build error. Two further WebKit points are lower risk. The attention module's two entry points share binding numbers 2-4 under auto layout. That's legal, and it would also fail by name. And the kernels' bitwise batch invariance is a claim about Tint and Metal on the desktop, so it shouldn't be extended to WebKit or a Vulkan driver without retesting.

## Four of Charlotte's failure paths leave no trace on a phone

Failures WebGPU reports through error scopes, mappings or device loss during a load or turn already reach the page by name (`src/core/residency/upload.h:185-223`; `src/wasm/bindings.cpp:615-634`). Four don't. **Uncaptured errors** go only to the worker console via `fprintf(stderr, ...)` (`src/core/gpu/device.cpp:40-49`). **Device loss** is recorded but never announced until the next turn is refused (`src/core/gpu/device.cpp:51-60`). **A hang without device loss** has no timeout. **An OS kill** leaves nothing, because nothing persists the last phase. On a phone the last two are the likeliest outcomes, and a tester without a Mac can't read a worker console. WebKit's `onuncapturederror` handling was itself fixed in the Safari 26.4 betas ([Releasebot, secondary](https://releasebot.io/updates/apple/safari); [Safari 26.4 notes](https://developer.apple.com/documentation/safari-release-notes/safari-26_4-release-notes)), so the iOS version belongs in every report. The passing self-check proves less than it seems. It runs a 4,096-element vector add with a literal workgroup size (`src/wasm/bindings.cpp:168-171`), so it exercises neither large allocations nor override-sized arrays.

The diagnostics therefore come first and are designed for these four cases. The worker forwards every uncaptured error and every device loss (reason and message) to the page as it happens. The page writes a breadcrumb to `localStorage` before each phase: device, preflight, load begin, kernel build, each upload chunk, finish, and each turn step. The worker can't reach `localStorage`, so the page writes on the worker's phase messages. On the next page load, an unfinished breadcrumb is shown as "the last session stopped during X", which turns a jetsam kill into a named phase. This is the breadcrumb pooled uses for the same purpose ([pooled #207](https://github.com/Nehanth/pooled/issues/207)). A notice that reports without cancelling appears after 20 s without progress during load or a turn, following the pattern the self-check's timeout already uses (`src/wasm/bindings.cpp:781-788`). A "copy diagnostics" control collects adapter info, granted limits, adapter maxima (already produced at `src/wasm/bindings.cpp:661-687`), user agent, budget, context offered, step cap, last phase and every error. On Android, `chrome://inspect#devices` gives full DevTools for the page and its worker ([Chrome DevTools](https://developer.chrome.com/docs/devtools/remote-debugging)), and `chrome://version` shows whether Chrome is a 32-bit build ([ghacks, 2021](https://ghacks.net/2021/03/13/google-is-pushing-64-bit-chrome-on-android)). On iOS the on-page record is the primary channel, because the Inspector can mask the hang. To confirm a kill, check the phone's Analytics Data for a `JetsamEvent` log. The notes don't source that path, so confirm it on the device. The page should also hold a Screen Wake Lock while a load or turn runs, and treat the tab being hidden as possibly ending the session, as pooled does ([pooled PR #258](https://github.com/Nehanth/pooled/pull/258)).

## The plan: capture, shrink, rewrite, shorten

Mobile mode turns on automatically when `web/platform.js` detects a phone, rather than behind an opt-in flag. The alternative leaves the 2 GiB desktop policy in place as the default phone path, and that's the one configuration already known to fail. The notice says the mode is experimental and names the budget in use. "Fits this device" (`web/model_view.js:102-106`) becomes "Fits a 768 MiB budget, not measured on this device", and the models stay unmeasured (`web/catalog.js:30`). Each change below is its own reviewable change with its own verification.

| Order | Change | Where | Verified by |
|---|---|---|---|
| 1 | Diagnostics: forward uncaptured errors and device loss to the page; `localStorage` phase breadcrumb shown on the next load; 20 s no-progress notice; copy-diagnostics control | `src/core/gpu/device.cpp`, `src/wasm/bindings.cpp`, `web/worker.js`, `web/app.js`, new pure breadcrumb module | JS unit tests of the breadcrumb reducer (an interrupted phase is reported on the next load); desktop check that a forced `device.destroy()` and an invalid pipeline both appear on the page by name |
| 2 | Phone memory policy in JS: 768 MiB on iOS, 1 GiB on Android, Gemma `rollbackReserve` 512 on phones, the same capped policy passed to preflight and load; labelled `?budget=` dev flag for bisection; reworded notice and fit text | `web/model_controller.js:42, 95-96`, `web/platform_notice.js`, `web/model_view.js` | JS unit test that preflight and load receive identical capped policies and `measured` stays false |
| 3 | Each workgroup array length becomes a bare override the host computes | `matmul.wgsl`, `attention.wgsl` and their `.cpp` launchers | Native tests produce bitwise-identical tokens before and after on desktop |
| 4 | Load-policy cap on prompt tokens per step (128 on phones, refused outside 1-512), and one step in flight on phones | `src/core/policy/policy.h`, `src/core/runtime/turn.cpp:21, 27`, `src/core/kernels/program.h`, `src/wasm/bindings.cpp:430-453` | Native test that a 950-token prompt yields the same tokens at caps of 512 and 128 |

Device testing uses the iPhone already in hand and, for Android, one Android 12+ phone with an Adreno or Mali GPU. No wider matrix is needed for an experimental mode. Each run follows the change it tests.

| Run | After | Device and browser | Configuration | What it settles |
|---|---|---|---|---|
| A | Change 1 | iPhone, Chrome | Today's 2 GiB default, Qwen3 | What actually killed the first attempt. Succeeds if the next page load names a phase and an error, even though the load fails |
| B | Changes 2, 3 | iPhone, Chrome and Safari | Qwen3 at 512 MiB, three short turns | Memory versus compiler. Kernels building here also confirm the rewrite path on WebKit |
| C | Change 4 | iPhone, Chrome | Qwen3 at 768 then 1,024 MiB; a 1,000-token prompt plus 128 generated tokens; three back-to-back loads in one session | The iOS budget ceiling and prefill timeouts. 768 MiB ships only if all three runs pass |
| D | Run C passes | iPhone, Chrome | Gemma at the budget C settled | Whether the second model fits. Llama stays refused on iOS by preflight below 801 MiB |
| E | Change 4 | Android phone, Chrome over USB DevTools | Qwen3, then Gemma, then Llama, at 1 GiB, same prompts as C | Driver compile, device loss and throughput on Dawn and Vulkan |

Success for the mode means four things. **Qwen3 loads at the phone budget on both phones.** It completes the 1,000-token prompt and 128 generated tokens with finite logits, three loads in a row without a reload. Every failure along the way showed up on the page with its phase and message. And a sustained decode rate is recorded. For calibration, LlamaWeb's low-power phones, including two iPhones, decoded at 4-17 tok/s ([arXiv 2605.20706](https://arxiv.org/pdf/2605.20706)). WebLLM managed about 5 tok/s for a 3B model on a Pixel 8 Pro ([web-llm #759](https://github.com/mlc-ai/web-llm/issues/759)). Greedy output is compared with desktop's and any divergence is recorded, not treated as failure, because bitwise agreement is claimed only on the desktop compiler.

## What only on-device testing can settle

| Question | Settled by |
|---|---|
| This iPhone's real page ceiling at its current uptime, and whether Chrome's WKWebView gets the same budget as Safari | Runs B and C in both browsers |
| Whether WebKit commits buffer memory at `createBuffer` (failure at load begin, where a scope can name it) or on first use (a later kill) | Run A's breadcrumb |

## Conclusion

The iPhone failure says less about Charlotte's kernels than about its policy. A budget sized for a desktop and spent mostly on KV cache that a phone conversation will never fill is a plausible way to die silently on iOS. And the codebase already has the seam to fix it: one budget value passed to both preflight and load. The deeper lesson is about observability. On desktop, every failure Charlotte expects arrives through an error scope. On a phone the likeliest failures arrive as nothing, a reload or a stalled queue, so the first change has to be the one that makes the next failure name itself.

The phone work also hardens the desktop build. Replacing override-expression array lengths with host-computed overrides removes a construct that one shipping WebGPU implementation is reported to reject. A per-step token cap gives the runtime a lever it'll want for any slower GPU. Neither change costs desktop performance, and both are verifiable on the desktop before a phone ever runs them.
